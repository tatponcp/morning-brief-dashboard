# สถาปัตยกรรม

ภาพรวมว่าระบบประกอบด้วยอะไร ข้อมูลเดินทางอย่างไร และทำไมถึงเลือกแบบนี้

## เว็บเดียว แยกด้วย route และสิทธิ์

```
/                      สรุปภาพรวมของวัน                 ← ลูกค้า
/s50-oi … /macro       6 section แยกหน้า                 ← ลูกค้า
/studio                IC Studio (ประกอบและเผยแพร่)      ← ทีม IC เท่านั้น
/studio/log            ความแม่นย้อนหลัง                  ← ทีม IC เท่านั้น
/studio-login          หน้าใส่รหัสผ่าน
/api/publish           รับ brief ที่ประกอบเสร็จ
/api/templates         คำมาตรฐานของทีม
/api/cron/set50        จดราคาปิด SET50 รายวัน
```

ทั้งฝั่งลูกค้าและฝั่ง IC ใช้ component ธีม และชนิดข้อมูลชุดเดียวกัน
พรีวิวใน Studio จึงตรงกับของจริงเสมอ สิ่งที่ต้องแยกคือสิทธิ์เข้าถึง ไม่ใช่ตัวเว็บ

เมนูฝั่งลูกค้าไม่มีลิงก์ไป `/studio` เพราะลูกค้าไม่ควรเห็นว่ามีหน้าเครื่องมือหลังบ้าน
แต่การกั้นจริงอยู่ที่ [`web/src/proxy.ts`](../web/src/proxy.ts) ไม่ใช่การซ่อนลิงก์

## เส้นทางข้อมูลของหนึ่งวัน

```
ภาพจากระบบเทรด / ชีตรายวัน
        ↓  IC แนบภาพหรือนำเข้า CSV
     IC Studio  ── เลือกสัญญาณจาก dropdown
        ↓         ระบบให้คะแนน + ร่างข้อความ (signal-forms.ts + scenarios.ts)
     ตรวจและแก้คำ
        ↓  กดเผยแพร่
   POST /api/publish
        ↓
  Supabase (ตาราง briefs + ถังเก็บภาพ)     ← ถ้าไม่ได้ตั้งค่า จะใช้ไฟล์ published.json แทน
        ↓  server component อ่านตอน render
     หน้าลูกค้า
        ↓  บันทึกคะแนนและเวอร์ชันกติกาไว้ในฉบับนั้น
  /studio/log เทียบกับราคาปิด SET50 ที่ cron จดไว้
```

## ชั้นของโค้ด

| ชั้น | ที่อยู่ | หน้าที่ |
|---|---|---|
| โมเดลสัญญาณ | `lib/signal-forms.ts` | dropdown ของแต่ละข้อ และกติกาให้คะแนน |
| คลังคำ | `lib/scenarios.ts` | ข้อความตั้งต้นของทุกสถานการณ์ และตัวประกอบข้อความ |
| คำของทีม | `lib/templates-store.ts` | คำที่ทีมบันทึกทับคำตั้งต้น เก็บที่ Supabase Storage |
| คะแนน | `lib/market-score.ts` | คะแนนรายข้อ ภาพรวม และเกณฑ์แบ่งช่วง |
| ปฏิทินสัญญา | `lib/contract-expiry.ts` | วันหมดอายุ S50 และช่วงย้ายสัญญา |
| ชั้นข้อมูล | `lib/brief-store.ts`, `lib/merge-brief.ts` | อ่านและเขียน brief รวมของที่เผยแพร่กับข้อมูลตั้งต้น |
| ความแม่น | `lib/signal-eval.ts`, `lib/signal-log.ts` | วัดผลย้อนหลังเทียบราคาจริง |
| สิทธิ์ | `proxy.ts`, `lib/studio-auth.ts`, `lib/studio-guard.ts` | กั้น `/studio` ด้วยรหัสผ่าน |

`lib/types.ts` คือสัญญาข้อมูลกลางที่ทุกชั้นใช้ร่วมกัน แก้ที่นี่แล้ว TypeScript จะชี้ให้เองว่าต้องแก้ตรงไหนอีกบ้าง

## การเก็บข้อมูล

**Supabase** เป็นตัวหลัก — ตาราง `briefs` เก็บเนื้อหาทั้งวันเป็น JSON ก้อนเดียวโดยใช้วันที่เป็นคีย์
เผยแพร่ซ้ำวันเดิมคือทับของเดิม ส่วนภาพเก็บใน Storage bucket `brief-images`
เปิด RLS ไว้และไม่สร้าง policy ใด ๆ ดังนั้น anon key อ่านไม่ได้เลย เข้าถึงได้เฉพาะ service role key
ที่อยู่ฝั่งเซิร์ฟเวอร์เท่านั้น ([schema](../web/supabase/schema.sql))

**โหมดไม่มี Supabase** — ถ้าไม่ได้ตั้งค่า ระบบจะอ่านจาก `src/data/published.json`
ทีมส่งออกไฟล์จาก Studio แล้ว commit ทับ เว็บจะอัปเดตตอน deploy รอบถัดไป
เหมาะกับช่วงทดลอง แต่ไม่เหมาะระยะยาวเพราะภาพจะทำให้ repo บวมเร็ว

ราคาปิด SET50 รายวันเก็บแยกที่ `config/set50-daily.json` ใน Storage เพราะเป็นข้อมูลต่อเนื่อง
ที่ไม่ผูกกับ brief ฉบับใดฉบับหนึ่ง

## งานอัตโนมัติ

| งาน | เวลา | ที่อยู่ |
|---|---|---|
| จดราคาปิด SET50 | ทุกวันทำการ 18:00 น. ไทย (`0 11 * * 1-5` UTC) | `app/api/cron/set50/route.ts` |
| ดึงราคา Gold / VIX / DXY / US10Y | สั่งเองด้วย `npm run fetch:macro` | `scripts/fetch-macro.mjs` |

cron ยอมรับคำขอจาก Vercel Cron, จาก `CRON_SECRET` หรือจากคุกกี้ของ IC ที่ล็อกอินอยู่
ทำให้กดจดย้อนหลังเองได้จากหน้า `/studio/log`

## การตัดสินใจที่สำคัญ

**ทำไมไม่ให้ AI วาดอินโฟกราฟิกทั้งใบ** — คุมคุณภาพไม่ได้และแก้ทีหลังยาก
ระบบจึงให้ภาพเป็นแค่ layer เดียว ส่วนกรอบ หัวข้อ จุดอธิบาย และบล็อกสรุป เว็บวาดเองทั้งหมด
ผลลัพธ์จึงเหมือนกันทุกวันและแก้ย้อนหลังได้

**ทำไมกติกาต้องมีเลขเวอร์ชัน** — เกณฑ์การอ่านสัญญาณจะถูกปรับเรื่อย ๆ
ถ้าไม่ประทับเวอร์ชันไว้ สถิติความแม่นจะปนกันระหว่างกติกาเก่ากับใหม่จนใช้ตัดสินใจไม่ได้

**ทำไมข้อความต้องแยกเป็นคลังคำ** — ให้ทุกคนในทีมพูดเหมือนกัน และแก้สำนวนได้จากหน้าเว็บ
โดยไม่ต้องแก้โค้ด ส่วนคำที่ระบบเขียนจากข้อมูลของวันนั้น เช่น ช่วงย้ายสัญญา จะต่อท้ายให้เสมอ
และไม่ถูกบันทึกปนเข้าไปในคำของทีม

**ทำไมเก็บ brief เป็น JSON ก้อนเดียว** — โครงของ brief เปลี่ยนบ่อยกว่าที่คิด
การเก็บเป็น JSON ทำให้เพิ่มฟิลด์ใหม่ได้โดยไม่ต้อง migrate ตาราง และฉบับเก่ายังอ่านได้เหมือนเดิม
ตัวรวมข้อมูล (`merge-brief.ts`) ทำหน้าที่เติมค่าที่ฉบับเก่าไม่มีให้เอง

## ข้อจำกัดที่รู้อยู่

- ข้อมูลข้อ 3 และ 5 มาจาก indicator ในโปรแกรมเทรด ดึงอัตโนมัติไม่ได้ ต้องแคปภาพ
- วันหยุดตลาดที่คำนวณอัตโนมัติมีเฉพาะวันหยุดที่วันที่ตายตัว วันหยุดตามจันทรคติต้องเพิ่มเอง
- การกั้น `/studio` เป็นรหัสผ่านชุดเดียวของทีม ไม่ใช่การยืนยันตัวตนรายคน
  ถ้าต้องแยกว่าใครแก้อะไรหรือเก็บ log ต้องเปลี่ยนไปใช้ Supabase Auth
- สถิติความแม่นต้องสะสมข้อมูลอย่างน้อย 20 วันทำการก่อนจะเริ่มเชื่อตัวเลขได้
